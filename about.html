About

Control maps and manuals for the Synthux Simple Touch. The library shows what every knob, fader, switch and pad does in a firmware; the designer is where those labels are made.

The directory is synthux-academy.github.io/community-instruments (source: Synthux-Academy/community-instruments). This site only reads it. The designer can write back to both: a label file for the repository, and an entry for the directory.

How the library finds labels

The official firmware (TouchBass, Touch FX, Touch String, Audrey II Touch, TouchVink) have labels checked by hand. For the community firmware under Community, the library tries, in this order:

  1. The creator's label file. A simple-touch-labels.json at the root of the repository's default branch, made in the designer. Shown as is. Faceplates from these files are not shown yet.
  2. Auto-extracted from the README. A script reads README.md, and a Markdown manual it links to, for control names (S30, P03, Switch A…) and the words next to them. These labels are a guess: they can be incomplete, shortened, or from another mode of the firmware. The library marks them as auto-extracted and lists the line each one came from.
  3. Nothing found. The drawing shows the Synthux names, with a link to the designer.

Controls without a label show their Synthux name, so you can still find your way around.

For firmware creators

Make your labels

  1. Open your firmware under Community in the library and follow Build the labels in the Designer. The designer opens with your name, author and repository filled in, plus anything the script found.
  2. Check and finish the labels: line 1 and line 2 per control, modifiers (P10 + knob, or a tapped mode pad), notes.
  3. Click Save file and rename the file to simple-touch-labels.json.
  4. Add it to the root of your repository, on the default branch. The library shows your labels from then on.

Or everything at once

Repository kit… in the designer downloads one .zip with a README (intro, control map image, control table, your notes, install and build), simple-touch-labels.json, the directory entry and a short HOW-TO. Pick how the firmware is built (libDaisy or Plugdata) and flashed (internal flash or the Daisy bootloader) and the README suggests the matching steps. Only you know the details, so check those parts and fill in what is marked TODO.

Let people play it

A libDaisy firmware can also run in the browser, built with simple-touch-web: the same code, compiled for a virtual Simple Touch with its knobs, faders, levers, pads, LED and optional OLED. The library then shows a Play button, and the drawing becomes the instrument. You decide whether that happens, and with which build:

  1. Split main() into a setup and a loop half and add the small workflow file from the simple-touch-web README. Every push then builds the firmware for the browser, checks that it boots, and publishes it on a simple-touch-web branch of your repository.
  2. Listen to the build on the test bench the run links to. Only you can say whether it sounds like your firmware.
  3. If it does, paste the emulator block from the run's summary into Browser build in the designer (under Firmware), save the file and add it to your repository as above. "embed": "allowed" lets the library play that build; "link-only" with a "url" only links to your own page. Add "oled": true if the firmware drives the optional OLED.

The block pins the build by its hash: the library refuses any other file, so a later build only plays here once you approve it. The build has to come from your own repository (its raw files or your Pages site). The library feeds it loops from simple-touch-web or the visitor's mic or own sound file.

Not in the directory yet?

In the designer, fill in Repository and Author link under Firmware, then click Directory entry…. It builds your projects/<id>.json, checks it the way the directory does, and opens a pull request on GitHub with the file filled in. Listing is not endorsement: Synthux does not review or test listed projects.

A README the script can read

If you'd rather keep everything in your README, write the controls as a table or a list, one control per line, using the Synthux names:

## Controls

| Control | Function |
|---|---|
| S30 | **Cutoff** |
| S36 | **Level** |
| P03 | **Kick** |

- **P10 + S30** · Resonance
- **Switch A** · Mode: notes / drone / off
  • Names it knows: knobs S30–S35 (or knob1–knob6), faders S36 and S37 (or left / right fader), pads P00–P11 (or P0–P11), switches S09-S10 and S07-S08 (or Switch A / B, SW1 / SW2, left / right switch).
  • The label is bold text, or the words after a separator (-, :, |, ·). Table rows count most, then lists and headings, then bold control names in sentences.
  • Modifiers are written as a pair: P10 + S30, P11 + left fader.
  • Ranges with one name per pad work too: P03–P09: kick, snare, hat, ….
  • Code blocks are skipped.

What is read and stored

  • Everything runs in your browser. Pages are read from synthux-academy.github.io, raw.githubusercontent.com and codeberg.org; nothing is sent anywhere else.
  • Text from repositories is only ever shown as text, never run as code.
  • The one exception is Play, and only when you press it: it runs the firmware build its author approved, checked against the hash in their label file, from their own repository or Pages site. It runs as WebAssembly in the page's audio thread, where it can only exchange sound, control positions and MIDI with the page. The loops come from jonwaterschoot.github.io; the mic is only opened if you choose it.
  • The designer keeps your work in this browser's storage. Nothing leaves it unless you save a file, copy a share link or open a pull request.
