About

Control maps and manuals for the Synthux Simple Touch. The library shows what every knob, fader, switch and pad does in a firmware; the designer is where those labels are made.

How the library finds labels

The official firmware (TouchBass, Touch FX, Touch String, Audrey II Touch) have labels checked by hand. For the community firmware under Community, the library tries, in this order:

  1. The creator's label file. A simple-touch-labels.json at the root of the repository's default branch, made in the designer. Shown as is, first in the creator's own look (the Creator theme), and with their faceplate if the file names one.
  2. Auto-extracted from the README. A script reads README.md, and a Markdown manual it links to, for control names (S30, P03, Switch A…) and the words next to them. These labels are a guess: they can be incomplete, shortened, or from another mode of the firmware. The library marks them as auto-extracted and lists the line each one came from.
  3. Nothing found. The drawing shows the Synthux names, with a link to the designer.

Controls without a label show their Synthux name, so you can still find your way around.

The README underneath

Below every firmware's manual, official or community, the library keeps the repository's own README.md, folded away. Open it and it is read from the default branch and drawn as GitHub draws it: headings, tables, code blocks, notes like > [!NOTE], ```mermaid flowcharts, and images and videos from where the README points. A video link on a line of its own plays in the page, and a YouTube link is embedded.

For firmware creators

Make your labels

  1. Open your firmware under Community in the library and follow Build the labels in the Designer. The designer opens with your name, author and repository filled in, plus anything the script found.
  2. Check and finish the labels: line 1 and line 2 per control, modifiers (P10 + knob, or a tapped mode pad), notes. If the firmware speaks MIDI, fill in the MIDI column too (e.g. CC 20 or note 36 ch 10): it becomes a column of the control table, and while someone plays the firmware here, each row shows the values that pass.
  3. Style it if you like: colours, sizes, a Google font and your own faceplate. The library shows your manual in this look first, as the Creator theme. Preview in library shows it there before you publish.
  4. Click Save file and rename the file to simple-touch-labels.json. With a faceplate of your own, Save file also downloads it, as the SVG or the image you uploaded; the label file names where it goes, img/faceplate.svg (or .png, .jpg…) unless you change it under Style.
  5. Add the label file to the root of your repository, on the default branch, and the faceplate at its path. The library shows your labels from then on.

Or everything at once

Repository kit… in the designer downloads one .zip with a README (intro, control map image, control table, your notes, install and build), simple-touch-labels.json, the directory entry and a short HOW-TO. Pick how the firmware is built (libDaisy or Plugdata) and flashed (internal flash or the Daisy bootloader) and the README suggests the matching steps. Only you know the details, so check those parts and fill in what is marked TODO.

Let people play it

A libDaisy firmware can also run in the browser, built with simple-touch-web: the same code, compiled for a virtual Simple Touch with its knobs, faders, levers, pads, LED and optional OLED. The library then shows a Play button, and the drawing becomes the instrument. You decide whether that happens, and with which build:

  1. Split main() into a setup and a loop half and add the small workflow file from the simple-touch-web README. Every push then builds the firmware for the browser, checks that it boots, and publishes it on a simple-touch-web branch of your repository.
  2. Listen to the build on the test bench the run links to. Only you can say whether it sounds like your firmware.
  3. If it does, paste the emulator block from the run's summary into Browser build in the designer (under Firmware), save the file and add it to your repository as above. "embed": "allowed" lets the library play that build; "link-only" with a "url" only links to your own page. Add "oled": true if the firmware drives the optional OLED.

The block pins the build by its hash: the library refuses any other file, so a later build only plays here once you approve it. The build has to come from your own repository (its raw files or your Pages site). The library feeds it loops from simple-touch-web or the visitor's mic or own sound file.

Visitors then drag the knobs and faders on the drawing, flip the levers and press the pads (higher up on a pad is harder; a right-click keeps one held, for combos), or play the pads from the computer keyboard. Web MIDI connects a keyboard to the firmware's USB MIDI and its output to a device; with a MIDI column in your labels, each row of the control table shows the values passing. On a phone, Full screen turns the drawing into the whole instrument.

Your own web app

Web app… in the designer packs your manual as a site for GitHub Pages: one page with the drawing in your look, the control table, your notes, your README and, with an approved browser build, Play. It runs on the same code as the library, copied into the .zip, so it keeps working whatever happens to this site. Preview ↗ in the dialog shows it first, following your edits.

  1. Put simple-touch-labels.json (and your faceplate) at the root of your repository, as above.
  2. Copy everything in the .zip's folder into a docs folder in your repository, and push.
  3. On GitHub: Settings › Pages, Source Deploy from a branch, your default branch, folder /docs, Save. A minute later it is at https://<you>.github.io/<repository>/.

Online, the page reads the label file from the root of your repository, so a build you approve later shows there without a new export. On your own computer (python -m http.server in the folder) it shows the copy beside it, so you can try changes before you push. Already using Pages for something else? Any subfolder works, e.g. docs/play/.

Not in the directory yet?

In the designer, fill in Repository and Author link under Firmware, then click Directory entry…. It builds your projects/<id>.json, checks it the way the directory does, and opens a pull request on GitHub with the file filled in. Listing is not endorsement: Synthux does not review or test listed projects.

A README the script can read

If you'd rather keep everything in your README, write the controls as a table or a list, one control per line, using the Synthux names:

## Controls

| Control | Function |
|---|---|
| S30 | **Cutoff** |
| S36 | **Level** |
| P03 | **Kick** |

- **P10 + S30** · Resonance
- **Switch A** · Mode: notes / drone / off
  • Names it knows: knobs S30–S35 (or knob1–knob6), faders S36 and S37 (or left / right fader), pads P00–P11 (or P0–P11), switches S09-S10 and S07-S08 (or Switch A / B, SW1 / SW2, left / right switch).
  • The label is bold text, or the words after a separator (-, :, |, ·). Table rows count most, then lists and headings, then bold control names in sentences.
  • Modifiers are written as a pair: P10 + S30, P11 + left fader.
  • Ranges with one name per pad work too: P03–P09: kick, snare, hat, ….
  • Code blocks are skipped.

What is read and stored

  • Everything runs in your browser. Pages are read from synthux-academy.github.io, raw.githubusercontent.com and codeberg.org; nothing is sent anywhere else. The export and README tools load from cdn.jsdelivr.net, pinned to fixed versions.
  • A README is only read when you open it. Its images and videos then load from wherever it points (as on GitHub), and a YouTube video from youtube-nocookie.com. It is cleaned first: no scripts, styles, forms or event handlers, and its flowcharts are drawn in mermaid's strict mode.
  • Text from repositories is only ever shown as text, never run as code. A creator's look passes as plain numbers, colours and words only, and their faceplate SVG is cleaned of scripts and outside links. A Google font in a creator's look is loaded from fonts.googleapis.com.
  • The one exception is Play, and only when you press it: it runs the firmware build its author approved, checked against the hash in their label file, from their own repository or Pages site. It runs as WebAssembly in the page's audio thread, where it can only exchange sound, control positions and MIDI with the page. The loops come from jonwaterschoot.github.io; the mic and MIDI devices are only opened if you choose them.
  • The designer keeps your work in this browser's storage. Nothing leaves it unless you save a file, copy a share link or open a pull request.
