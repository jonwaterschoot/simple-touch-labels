Step by step

From a firmware to the library: labelled, playable, and listed in the Synthux community directory. Every step ends with checks. Tick them as you go: this browser remembers them. To share a firmware without this site, see A README for any firmware for the minimum.

Where do you start?
Built with

The order

  1. Your repository (step 1): public on GitHub, with a README and a release with the .bin. Everything else points at it.
  2. The pull request to the community directory (step 2), as soon as step 1 is done. Don't wait for labels, a browser build or a page. A person reviews it, and that can take days.
  3. While you wait (steps 3 to 5): labels, the browser build and a page of your own. None of them need the review. Commit them to your default branch.
  4. After the merge (step 6): the library lists your firmware with whatever is on your default branch by then. The directory entry doesn't change for a new label or build.

1. Your repository

  1. 1a
    Set upEditorPlugdataGitGitHub

    An editor (VS Code, say), Git and a GitHub account. For libDaisy, the Daisy Toolchain builds and flashes.Plugdata with its compiler toolchain, which Plugdata installs itself, plus Git and a GitHub account. The Daisy can't run a .pd file: Plugdata's compiler (hvcc) translates the patch into C++ and builds a .bin from it. That build needs your patch, its abstractions in the same folder, and the Simple Touch board file simple_touch.json.

    In detail
    1. Help (optional): an AI chat assistant can walk you through these installs and explain an error. Give it the command you ran and its full output. For example Claude (its app, or Claude Code inside VS Code), the Copilot chat built into VS Code (free with a GitHub account), or Antigravity, an editor with an assistant of its own. Read what it asks you to run before you run it.
    2. GitHub: make an account at github.com/signup.
    3. Git, for the repositories:
      • Windows: Git for Windows, with the installer's defaults. It brings Git Bash, the terminal the Daisy tools expect.
      • macOS: in Terminal, xcode-select --install. It installs Git and make, not Xcode.
      • Linux: sudo apt install git, or your distribution's package.
    4. The Daisy Toolchain: the ARM compiler (arm-none-eabi-gcc), make and dfu-util. The Daisy docs have a page per system:
      • Windows: the Daisy Toolchain installer.
      • macOS: the Daisy Toolchain .pkg (right-click › Open if macOS blocks it), or with Homebrew: brew install make gcc-arm-embedded dfu-util.
      • Linux: build-essential and dfu-util from the package manager, and the Arm GNU toolchain on your PATH, as the Linux page shows.
    5. Python 3.8 or later, from python.org. On Windows, not the Microsoft Store version, and tick Add python.exe to PATH in the installer. libDaisy's helper.py needs it to make a new project. It also serves a folder as a local website (python -m http.server) to try a web app before you push it.
    6. VS Code (optional): Plugdata doesn't need it. It helps with the README and Git, but GitHub Desktop (below) and any text editor do too. Download it from code.visualstudio.com and run the installer. Start it from the Start menu (Windows) or Applications (macOS). Source Control in its left bar shows Git once Git is installed. If it doesn't, restart VS Code.
      • Windows: make Git Bash its terminal. Open a terminal (Terminal › New Terminal), then the ⌄ beside the + › Select Default Profile › Git Bash. In PowerShell, make can stop with CreateProcess(NULL, mkdir build, ...) failed.
      • Extensions (View › Extensions, Ctrl+Shift+X): C/C++ by Microsoft marks errors in the code and jumps to libDaisy's definitions (F12). Cortex-Debug by marus25 is only for a debug probe.
    7. Check the tools: in a new terminal, each of these prints a version. If one says "command not found", its install didn't reach your PATH: restart VS Code, or the computer, and try again.
      git --version
make --version
arm-none-eabi-gcc --version
dfu-util --version
python --version
      On macOS and Linux the last one is python3 --version.
    8. Sign in: the Accounts icon at the bottom of VS Code's left bar › Sign in with GitHub. Your browser asks you to allow it. VS Code can then push to your repositories.
    9. Your name in commits: Git writes a name and email into every commit, and on GitHub they are public. Use the private address from GitHub's Settings › Emails, which ends in @users.noreply.github.com. In VS Code's terminal, once per computer:
      git config --global user.name "Your Name"
git config --global user.email "12345678+you@users.noreply.github.com"
      GitHub Desktop (below) sets both when you sign in, so with it you can skip these two lines.
    10. A home for your repositories: one folder that holds every repository you clone, each in a folder of its own. For example Documents\GitHub in your user folder on Windows, ~/Documents/GitHub on macOS. GitHub Desktop clones into that folder by default. In VS Code's terminal:
      mkdir ~/Documents/GitHub
    11. GitHub Desktop (optional): from desktop.github.com. Sign in with your GitHub account when it starts. It shows every changed line before you commit, commits and pushes with a button each, and clones from a web address with File › Clone repository… › URL. Open in Visual Studio Code opens the repository's folder in VS Code.
    12. A first flash: the Daisy examples, with Blink:
      cd ~/Documents/GitHub
git clone --recurse-submodules https://github.com/electro-smith/DaisyExamples
      In VS Code, File › Open Folder… › DaisyExamples/seed/Blink. Put the Simple Touch in its bootloader (hold BOOT while you plug in USB), then Ctrl+P (Cmd+P on macOS) and type task build_and_program_dfu. The first time, run task build_all before it: it builds libDaisy and DaisySP. The Daisy Seed's own LED blinks. A closing Error 74 from dfu-util is normal. If dfu-util finds no device on Windows, the Zadig page sets its USB driver.
    13. Plugdata: download it from plugdata.org and run the installer.
    14. The compiler toolchain: the first time you open Plugdata's export dialog, it offers to install the toolchain: hvcc and the ARM compiler for the Daisy. There is nothing to install by hand.
    15. How a patch reaches the Daisy: the Daisy can't read .pd files. hvcc translates the patch into C++, the toolchain compiles that into a .bin, and Plugdata flashes it. hvcc translates most vanilla Pd objects, not all of them, and no externals. Turn on Menu › Heavy Compiler › Toggle Compiled Mode while you patch: Plugdata then offers only objects hvcc can translate.
    16. What the compile needs:
      • Your .pd patch.
      • Every abstraction it uses, in the same folder as the patch.
      • A board file: a JSON that maps the Simple Touch's knobs, faders, switches and the pads of its MPR121 touch sensor to the names your patch receives. Download simple_touch.json from hvcc-examples-daisy.
    17. A first flash: open a patch, then the export dialog. Pick Electro-Smith Daisy, choose simple_touch.json as the custom JSON for the target board, set the export type to Binary, and flash. The Simple Touch has to be in its bootloader (hold BOOT while you plug in USB).
  2. 1b
    Make the firmware

    Start from an official firmware (TouchBass, Touch String, …), a community one, or nothing.Start from simple_touch_template.pd in hvcc-examples-daisy. It receives every control and prints its changes, and passes audio from input to output. Compile it with simple_touch.json, debug printing on and patch size Big, then build your patch from there. If you build on someone's code, keep their licence and credit them in the README.

    In detail
    1. Start from an official firmware: TouchBass or Touch String. Their code already sets up the Simple Touch's pads, knobs and faders. A bare template is on the way. Copy one into your repositories folder, under the name of yours:
      cd ~/Documents/GitHub
git clone --recursive https://github.com/Synthux-Academy/TouchBass
    2. Open it: in VS Code, File › Open Folder… › Documents/GitHub/. Terminal › New Terminal opens a terminal in that folder.
    3. Build and flash it as Blink in step 1a: Ctrl+P, task build_all the first time, then task build_and_program_dfu with the Simple Touch in its bootloader. In the terminal it is make and make program-dfu, in the folder with the Makefile. Then change the code, and build and flash again until it plays as you want.
    4. Make a folder Documents/GitHub/ with simple_touch_template.pd and simple_touch.json in it. Save your patch there under its own name, with every abstraction it uses next to it.
    5. Export and flash it as in step 1a, with debug printing on and patch size Big. The template prints every control's changes, so you see which receive belongs to which knob, fader and pad.
    6. Keep the original licence file, and name whose code it builds on in your README.

    In detail

4. Make it playable (libDaisy only, for now)

    
simple-touch-web runs libDaisy firmware. A Plugdata patch can't be played in the browser yet; skip to step 5.

    
    
      
  1. 4a
    
        
    Setup and loopsimple-touch-web
    
        
    Split main() into Setup() and a Loop() that runs one pass, as the simple-touch-web README shows. Leave out what a browser can't do (flash writes, bootloader jumps) with #ifdef SIMPLE_TOUCH_WEB.
    
        
    In detail
          
    static void Setup() { /* main() up to the loop */ }
static void Loop()  { /* one pass of the loop */ }

#ifdef SIMPLE_TOUCH_WEB
#include "simple_touch_web.h"
ST_WEB_FIRMWARE(Setup, Loop)
#else
int main() {
    Setup();
    while (true) Loop();
}
#endif
    
          
      
            
    1. Move everything in main() before the loop into Setup(), and the body of the loop into Loop(). Variables that both use go to file level.
      2. 
            
    2. In the browser the clock only moves between passes, so a wait on System::GetNow() inside Loop() never ends. End the browser pass with System::Delay(ms) under #ifdef SIMPLE_TOUCH_WEB, and keep the wait for the Seed.
      3. 
            
    3. Add build-web to .gitignore.
      4. 
            
    4. The simple-touch-web README has the rest, such as leaving out a syscalls.cpp.

A README for any firmware

    
For anyone sharing Simple Touch firmware, listed here or not. A player with the instrument in front of them looks up one control at a time, so the controls go in a table, in README.md at the root of the repository.

    
The minimum

    
    
      
  1. What it is: one or two sentences on what it does, and that it runs on the Simple Touch.
    2. 
      
  2. Install: a link to the newest .bin, how to flash it, and whether it needs the Daisy bootloader.
    3. 
      
  3. Controls: a table with one row per control the firmware uses. Name each control the same way throughout: knobs S30–S35, faders S36 (left) and S37 (right), pads P00–P11, and the left and right switch.
    4. 
      
  4. Modifiers, if it has them: a row for each function that needs a held pad, written as P10 + S30.
    5. 
      
  5. Modes, if a switch changes what the controls do: a heading and a table for each position.
    6. 
      
  6. Licence and credits: the licence, and whose code it builds on.
    7. 
    

    
Optional but preferred

    
    
      
  • Releases: publish each version as a GitHub release with its .bin attached (step 1). The address /releases/latest then always points to the newest version.
    • 
      
  • The Synthux community directory: add your firmware to the community directory with a pull request on its repository. Directory entry… in the designer fills in the file for you (step 2). Listed Simple Touch firmware also appears in this site's library.
    • 
    

    
Template


# My Firmware

A tape delay for the Synthux Simple Touch.

## Install

Download the newest `.bin` from [Releases](https://github.com/you/my-firmware/releases/latest)
and flash it with the [Daisy Web Programmer](https://flash.daisy.audio/).
Hold BOOT while plugging in USB. It does not need the Daisy bootloader.

## Controls

| Control | Function | Detail |
|---|---|---|
| S30 | Time | 10 ms to 2 s |
| S31 | Feedback | Fully right self-oscillates |
| S36 | Level | Output volume |
| Left switch | Mode | Up: notes. Down: presets |
| P10 | Modifier | Hold with a knob |
| P10 + S30 | Width | Mono to wide |

### Notes (Left switch up)

| Control | Function | Detail |
|---|---|---|
| P03–P09 | Play notes | Hold to sustain |

### Presets (Left switch down)

| Control | Function | Detail |
|---|---|---|
| P03–P06 | Recall a preset | Tap to recall |

## Licence and credits

MIT. Built on [DaisySP](https://github.com/electro-smith/DaisySP).

    
Where it goes

    
    
      
  • In the root README: GitHub shows that file on the repository's front page. If the full manual is in another file, link it from the root README with the word manual in the link text: [Manual](docs/manual.md).
    • 
      
  • In Markdown: a PDF or HTML manual can sit next to it. The table stays in Markdown.
    • 
      
  • In a table: explain the sound and the ideas in paragraphs below it, and name every control in the table as well.
    • 
    

    
Worth adding

    
A picture of the panel with its labels, a table of MIDI CCs, a demo recording, what changed in each version, and how to build from source.

    
On this site

    
The library reads a table like this as auto-extracted labels. A label file from the designer replaces them (step 3), and Repository kit… writes a README from your labels. The script understands:

    
    
      
  • Names: knobs S30–S35 (or knob1–knob6), faders S36 and S37 (or left / right fader), pads P00–P11 (or P0–P11), switches S09–S10 and S07–S08 (or Switch A / B, SW1 / SW2, left / right switch).
    • 
      
  • The label: bold text, or the words after a separator (-, :, |, ·). Table rows count most, then lists and headings, then bold control names in sentences.
    • 
      
  • Modifiers as a pair: P10 + S30, P11 + left fader.
    • 
      
  • Ranges with one name per pad: P03–P09: kick, snare, hat, …. Pairs too: | P10 / P11 | Octave down / up |.
    • 
      
  • Modes: a heading per switch position that names it, such as ### Seq (SW2 Up), with that mode's table under it. Labels from different modes are never mixed, and everything outside the mode sections counts for all of them.
    • 
      
  • Code blocks are skipped.
