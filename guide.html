Step by step

From a firmware to the library: labelled, playable, and listed in the Synthux community directory. Every step ends with checks. Tick them as you go: this browser remembers them. To share a firmware without this site, see A README for any firmware for the minimum.

Where do you start?
Built with

The order

  1. Your repository (step 1): public on GitHub, with a README and a release with the .bin. Everything else points at it.
  2. The pull request to the community directory (step 2), as soon as step 1 is done. Don't wait for labels, a browser build or a page. A person reviews it, and that can take days.
  3. While you wait (steps 3 to 5): labels, the browser build and a page of your own. None of them need the review. Commit them to your default branch.
  4. After the merge (step 6): the library lists your firmware with whatever is on your default branch by then. The directory entry doesn't change for a new label or build.

1. Your repository

  1. 1a
    Set upEditorGitGitHub

    An editor (VS Code, say), Git and a GitHub account. For libDaisy, the Daisy Toolchain builds and flashes. For Plugdata, Plugdata with its Daisy export, and the Simple Touch board file simple_touch.json.

  2. 1b
    Make the firmware

    Start from an official firmware (TouchBass, Touch String, …), a community one, or nothing.Start from simple_touch_template.pd in hvcc-examples-daisy. It receives every control and prints its changes, and passes audio from input to output. Compile it with simple_touch.json, debug printing on and patch size Big, then build your patch from there. If you build on someone's code, keep their licence and credit them in the README.

  3. 1c
    A public repositoryGitHub

    On GitHub, New repository, set to Public, then push your code. The directory needs GitHub; the library also reads Codeberg.

  4. 1a
    Check the repositoryGitHub

    Its default branch is where everything below goes: the library and the designer read nothing else. You see it on the repository's front page and under Settings › Branches, usually main. Merge work from other branches before you check anything in the library.

  5. 1d
    A README

    What the firmware does, how to install it, and a table of its controls. A README for any firmware has the minimum and a template. The designer's Repository kit… can write a full one with the control map later (step 3c), which you can merge into yours. A short README is enough for the pull request.

  6. 1e
    A release with the .binGitHub

    Releases › Draft a new release, a tag such as v1.0.0, and the firmware attached, named in lowercase with hyphens: my-firmware-v1.0.0.bin. People flash that file with the Daisy Web Programmer, or with Upload to device… on the firmware's page in the library, which takes the latest release and says whether it needs the Daisy bootloader. The directory recommends it (it warns without one) and will need it for one-click flashing later.

2. The pull request to the community directory

The Synthux community directory is the repository Synthux-Academy/community-instruments: one JSON file per firmware, in projects/. You add yours with a pull request. Open it as soon as step 1 is done: a public repository, a README with a controls table, and a release with the .bin. Labels, a browser build and a page can follow while it's reviewed.

  1. 2a
    Open your firmware in the designerDesigner

    Two ways in. Both fill in the labels too, so step 3 starts from them.

    From your repository

    Open repository… and paste its address, or open it in the designer ↗ with the address at the top of this page. The designer reads simple-touch-labels.json from the default branch. Without one, a script fills in the labels from the README and a manual it links to. Name, author and repository are filled in. The repository doesn't have to be listed yet.

    or
    From a README file

    Open file… and pick a README.md on your computer: for a README you haven't pushed yet. A script reads its labels and modes, and the name from its first # heading. Fill in the repository under Firmware yourself.

  2. 2b
    Directory entryDesignerGitHub

    Under Firmware, fill in what's missing: name, author, a one-line description (up to 200 characters) and the repository. Then Directory entry… checks the entry the way the directory does. Open pull request… opens GitHub with projects/<id>.json filled in. GitHub makes a fork for you first if you need one. Commit the file, then create the pull request.

    If you can write to community-instruments, GitHub offers to commit straight to main. Pick the option to create a new branch and start a pull request instead. Without the designer: fork the repository, add the file as CONTRIBUTING.md describes, and open a pull request.

    If the check is red, the pull request's Files changed tab marks what's wrong in your file (/author/url is the url in author). Fix it in your fork, on the same branch, and push: the check runs again.

  3. 2c
    The reviewGitHub

    A reviewer checks that the repository matches the entry, has a README and targets the Simple Touch. Nobody tests the firmware. It can take days. Your pull request is under Pull requests, and GitHub emails you when someone comments. If the reviewer requests changes, edit the file in your fork, on the same branch: the pull request updates and the check runs again.

    Go on with step 3 now. Everything you commit to your default branch is in the library once the entry is merged.

While you wait. Steps 3 to 5 don't need the review, and none of them change the directory entry. Each one is a commit to your default branch.

3. Labels

  1. 3a
    Label every controlDesigner

    If you opened your repository or README in step 2a, the labels are filled in. If a script read them from a README, check every one. Otherwise start from Blank, or from the official firmware you built on. Reference names: Synthux shows S30, P03 and so on under each label. Then, in the Labels tab:

    • Line 1 for what a control does, line 2 for detail (a switch's positions: "off / on / latch").
    • Pads held for a second function: tick Mod, and fill their column for what the other controls do while it's held (or after it's tapped: click hold for tap).
    • A function that needs pads held together, such as P10 + P11: add them under Held together. They get one column of their own, and neither pad has to be a modifier by itself.
    • A switch that changes what everything does, such as a playmode switch: Modes. The labels without a mode are the print set, as wide as fits every mode. If the README has a heading per switch position, Fill the modes from the README reads them.
    • The MIDI column if it sends or listens to MIDI, and Notes for what doesn't fit on a label.
  2. 3b
    Your look optionalDesigner

    The Style tab: a faceplate of your own (download the template there), colours, label boxes; the font in the toolbar. The library shows it as the Creator theme.

  3. 3c
    Into the repositoryDesignerGitHub

    Repository kit… downloads a .zip; its HOW-TO.txt says where each file goes. Put simple-touch-labels.json at the root, the control map at docs/ (a new folder, even if you have a doc/), and your faceplate at the path the label file names. If you already have a README, keep it at the root and copy in the parts you want. Then commit to the default branch.

    GitHub caches raw files for a few minutes, so a new push can take that long to show.

4. Make it playable (libDaisy only, for now)

simple-touch-web runs libDaisy firmware. A Plugdata patch can't be played in the browser yet; skip to step 5.

  1. 4a
    Setup and loopsimple-touch-web

    Split main() into Setup() and a Loop() that runs one pass, as the simple-touch-web README shows. Leave out what a browser can't do (flash writes, bootloader jumps) with #ifdef SIMPLE_TOUCH_WEB.

  2. 4b
    The workflowGitHub Actions

    Add .github/workflows/browser-build.yml from the simple-touch-web README and push. Every push then builds the firmware for the browser, checks that it boots, and adds the build to a simple-touch-web branch.

  3. 4c
    Listen, then approveTest benchDesigner

    In the designer, under Browser build, Find builds in the repository lists the builds with a Test bench link. Listen there. If it sounds like your firmware, tick "drives the OLED" if it has one, then Use this build, Save file, and commit the label file again.

5. A page of your own optional

  1. 5a
    Web appDesignerGitHub Pages

    Web app… packs your manual as a site: copy the folder into docs/ on the default branch, then Settings › Pages: Deploy from a branch, your default branch, /docs. It works whether or not the firmware is listed. Link it from your README.

6. After the merge

  1. 6a
    In the libraryLibrary

    The directory publishes on every merge, and the library lists your firmware under Community. It reads your repository each time, so labels and builds you add later show up by themselves.

Later: keeping it up to date

  • Labels: designer › Open file… your simple-touch-labels.json, edit, Save file, commit.
  • A new firmware version: a new release with its .bin; with a browser build, approve the new build (Find builds › Use this build) once you've listened to it. Until then the library keeps playing the approved one.
  • The directory entry only changes when the name, description or repository does.

A README for any firmware

For anyone sharing Simple Touch firmware, listed here or not. A player with the instrument in front of them looks up one control at a time, so the controls go in a table, in README.md at the root of the repository.

The minimum

  1. What it is: one or two sentences on what it does, and that it runs on the Simple Touch.
  2. Install: a link to the newest .bin, how to flash it, and whether it needs the Daisy bootloader.
  3. Controls: a table with one row per control the firmware uses. Name each control the same way throughout: knobs S30–S35, faders S36 (left) and S37 (right), pads P00–P11, and the left and right switch.
  4. Modifiers, if it has them: a row for each function that needs a held pad, written as P10 + S30.
  5. Modes, if a switch changes what the controls do: a heading and a table for each position.
  6. Licence and credits: the licence, and whose code it builds on.

Optional but preferred

  • Releases: publish each version as a GitHub release with its .bin attached (step 1). The address /releases/latest then always points to the newest version.
  • The Synthux community directory: add your firmware to the community directory with a pull request on its repository. Directory entry… in the designer fills in the file for you (step 2). Listed Simple Touch firmware also appears in this site's library.

Template

# My Firmware

A tape delay for the Synthux Simple Touch.

## Install

Download the newest `.bin` from [Releases](https://github.com/you/my-firmware/releases/latest)
and flash it with the [Daisy Web Programmer](https://flash.daisy.audio/).
Hold BOOT while plugging in USB. It does not need the Daisy bootloader.

## Controls

| Control | Function | Detail |
|---|---|---|
| S30 | Time | 10 ms to 2 s |
| S31 | Feedback | Fully right self-oscillates |
| S36 | Level | Output volume |
| Left switch | Mode | Up: notes. Down: presets |
| P10 | Modifier | Hold with a knob |
| P10 + S30 | Width | Mono to wide |

### Notes (Left switch up)

| Control | Function | Detail |
|---|---|---|
| P03–P09 | Play notes | Hold to sustain |

### Presets (Left switch down)

| Control | Function | Detail |
|---|---|---|
| P03–P06 | Recall a preset | Tap to recall |

## Licence and credits

MIT. Built on [DaisySP](https://github.com/electro-smith/DaisySP).

Where it goes

  • In the root README: GitHub shows that file on the repository's front page. If the full manual is in another file, link it from the root README with the word manual in the link text: [Manual](docs/manual.md).
  • In Markdown: a PDF or HTML manual can sit next to it. The table stays in Markdown.
  • In a table: explain the sound and the ideas in paragraphs below it, and name every control in the table as well.

Worth adding

A picture of the panel with its labels, a table of MIDI CCs, a demo recording, what changed in each version, and how to build from source.

On this site

The library reads a table like this as auto-extracted labels. The format lists what the script understands. A label file from the designer replaces those labels (step 3), and Repository kit… writes a README from your labels.
