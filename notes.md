## Synthux Lab

**Known (2026-10-28):**
- The official repos (TouchBass, TouchString, AudreyTouch, TouchFX) have no web build in public: no wasm or emscripten code, and no web branches. Whatever lab.synthux.academy runs is built and hosted outside them.
- All four use a standard libDaisy Makefile and a blocking main loop (`while(1)`, or `app.loop()` in TouchFX). That is the one change simple-touch-web needs.
- None of them uses what the emulator lacks (`PersistentStorage`, QSPI writes, timer callbacks, SPI displays). AudreyTouch (32 MiB) and TouchFX (8 MiB) reserve SDRAM pools with `DSY_SDRAM_BSS`, which the emulator makes plain memory. TouchFX's TRS MIDI stays silent.

**Unknown, needs eyes or an answer.** lab.synthux.academy refuses automated access:
- WebAssembly of the real firmware, a JS model, or recordings? One module per firmware or one bundle? Which exports does its JS call (its ABI)?
- Where the files are hosted, with what CORS headers and licence.
- Deep links per firmware; whether it may be framed (`X-Frame-Options`, CSP `frame-ancestors`).

**DevTools check (30 min, no answer from Synthux needed):** open Lab, Network tab filtered on `wasm`, `js`, `worklet`; start a firmware; note every URL and size. In Sources, find `audioWorklet.addModule` and `WebAssembly.instantiate*` and list the exports it calls. Note the response headers (`Access-Control-Allow-Origin`, `X-Frame-Options`, `Content-Security-Policy`) and any licence or repository link. Write the results here.

## Three ways to get the officials playing

| Path | Effort | Risk | When |
|---|---|---|---|
| A. Link to Lab (`embed: link-only`, `url` = Lab page) | an hour | none; Lab keeps ownership | as soon as there are deep links and a yes |
| B. Load Lab's wasm in the library's player | an adapter per ABI | undocumented ABI that can change, CORS, no sha pin, licence unclear | only if Synthux publishes the runtime and invites it |
| C. Build the officials with simple-touch-web (fork, then PR) | about half a day per firmware | low; same trust model as TouchVink | the main track |

B breaks the library's rule that a build is played only from the firmware's own repository, pinned by sha256, and means maintaining a guess at someone else's interface. If Lab turns out to be open and repo-hosted, B becomes C.

The Synthux site will most likely keep its own manual and player. The shared layer worth agreeing on is the data in each firmware repository (labels, faceplate, browser build), not the UI. Lab and the library can both render from it.

## Hosting the `.wasm`: not as a release asset

Tested 2026-10-28 with `curl -I -H "Origin: …"`:
- `github.com/<owner>/<repo>/releases/download/…` answers 302 to `release-assets.githubusercontent.com`, and neither response has `Access-Control-Allow-Origin`. A page on another site can't fetch it.
- `raw.githubusercontent.com/…` sends `Access-Control-Allow-Origin: *`. GitHub Pages does too.

So the `.bin` stays in Releases (people download it), and the `.wasm` goes on the repository's `simple-touch-web` branch, which is what simple-touch-web's `build-firmware.yml` does. The library already accepts only those two hosts (`buildHosted` in `core.js`).

## Case study: TouchPlaited

Why it makes a good test: large (a 228 KB main file, all of Plaits and stmlib vendored as `.cc` sources), hardware-tuned (QSPI boot, ITCM code placement, a register-level QSPI settings journal), with an OLED UI, USB and TRS MIDI, mode-dependent controls, and a web visualizer of its own. Most community firmwares will be simpler.

### Browser build (2026-10-28)

Firmware, branch `browser-build` from `main` (uncommitted):
- `TouchPlaited.cpp`: `main()` split into `Setup()` (up to `StartAudio`) and `Loop()` (one pass; each `continue` became `return`, `last_cpu_print` became a file static), registered with `ST_WEB_FIRMWARE` under `#ifdef SIMPLE_TOUCH_WEB`. The ITCM copy constructor is left out of the browser build; it needs linker symbols that only exist on the Seed.
- `synth/settings_journal.cpp`: under `SIMPLE_TOUCH_WEB`, `Init` returns false and `Tick` does nothing. No flash, so every boot is a first boot (random engine, as on a fresh unit).
- `Makefile`: `ifdef SIMPLE_TOUCH_WEB` → `C_DEFS += -DTEST`. stmlib then uses plain C instead of ARM asm (`ssat`, `usat`, `vsqrt`) and drops `.ramtext`. Checked: `TEST` changes nothing else in the compiled sources. VCV Rack's Mutable ports use the same define.
- `Makefile`: `synth/patterns_gen.h` is generated by make and git-ignored, and simple-touch-web only asks make for its variables, so a fresh checkout (CI) would miss it. Under `SIMPLE_TOUCH_WEB`, `stw-vars` now depends on it. Tested from a clean state: regenerated byte-identical, same build hash. The generator runs `python`, so check that the CI runner has it under that name.
- `.gitignore`: `build-web/`.

simple-touch-web (uncommitted):
- `make/Makefile` prints `CC_SOURCES`, and `build.mjs` compiles them as C++. Before this, every `.cc` file was silently skipped and the link would fail on Plaits.
- `build.mjs` runs make with `SIMPLE_TOUCH_WEB=1` on the command line, so a firmware's Makefile can add browser-only flags.
- Backwards compatible: TouchVink builds to the same sha256 with and without the change.

Result: 465 KB. The smoke test boots it (71-frame, 2 s boot film on the OLED). P3, P4, P5 and P9 each play at about -4.7 dBFS peak and -16 dBFS RMS and send USB MIDI. The OLED shows the play screen. It renders 5 s of audio in 34 ms (148× real time, one voice at a time, desktop).

Hardware: the same branch built with `make clean && make` and flashed to a Simple Touch works as before (2026-10-28).

Nothing else needed changing: `__disable_irq`, `__DSB`, `__ISB`, `DSY_SDRAM_BSS`, `CpuLoadMeter`, the SSD1306 driver subclass, the USB and UART MIDI handlers and the D25 clock-out GPIO all work as they are.

### Tested in the browser (2026-10-28)

The test bench and the library preview behave the same. Audio plays; the drums start and stop with P2 + P11 from the keyboard. With a mouse alone, a combo couldn't be played: now a right-click keeps a pad held, on both pages. The test bench had QWERTY keys only: now it plays by key position with a QWERTY / AZERTY switch, as the library does. The LED blinked only in the boot film: fixed, see below. Second round (build `8acf93d464ec`, simple-touch-web v1.2): the LED blinks and right-click hold both work, on the test bench and in the library preview.

### Things to check in the browser

- **LED blinks inside a pass** (fixed in simple-touch-web v1.2). In the emulator, `System::Delay()` inside a main-loop pass only advances that pass's clock and returns, and the page reads the LED between passes. TouchPlaited draws its blinks inside one pass (`set_led(true); delay_serviced(130); set_led(false); delay_serviced(70);`), so in the browser the LED only blinked during the boot film. The board now queues each LED change with the pass's clock, and `st_led()` shows it when the audio gets there. Smoke test, P0+P2 held 0.4 s: 0 LED changes before, 4 after. TouchVink unchanged.
- **Waits on the audio thread.** The P0+P2 stage wait loops on `GetNow() - t0 < 500` while the audio interrupt changes the hold counters. In the emulator the audio callback doesn't run during a pass, so the wait always runs its full 500 virtual ms. It ends because `delay_serviced(5)` advances the clock, so it can't hang, but releasing early won't cut it short.
- **CPU on a phone** with seven voices, the sequencer and four reverb/delay groups busy. The Seed needed ITCM to fit; a phone's AudioWorklet may need a larger block or fewer voices.
- **MIDI**: the firmware sends a lot (telemetry SysEx for the visualizer). Check that the library's MIDI rows and Web MIDI out cope.

### Labels: what the format has to carry

- SW2 picks the mode (Seq, Arp/Mel, Pitch), and SW1 means something different in each (IDM / Techno / Electro; Hold / Arp / Rec; Minor / Chromatic / Major).
- Knob meanings follow the Plaits engine (24 models, per-engine Harmonics / Timbre / Morph names in `ENGINE_KNOBS`).
- The visualizer's `controls-meta.ts` already holds controls, pads, switch positions, CCs and notes. It is the source to copy from in the designer. A converter would be quicker, but doing it by hand in the designer is the point of the case study.
- Likely fit: main labels for the generic function, modifier columns as the three modes (tapped mode switch, as TouchVink does with P00/P02), engine detail in the notes. Where that falls short is input for the "modes" item in the roadmap.

### Labels: the import (2026-10-28)

The first import mixed modes: knobs from the manual's Basic Pitch table, pads from the Seq drum table (the Basic Pitch row `P3–P9 | Play notes` was skipped as a range), S35 from Arp/Mel, P10/P11 from Recording. The import now reads mode sections (headings naming a switch position), table ranges and `P10 / P11` pairs, and fills one mode at a time:

| | Basic Pitch | Arp/Mel | Seq |
|---|---|---|---|
| S31…S34 | Decay, Harmonics, Timbre, Morph | Decay, Division, Swing, Density | Tempo, Shuffle, Pattern density, Step chance |
| SW1 | Scale | Sub-state | Genre |
| P3–P9 | Play notes | Arp | Kick, Snare, Cl. hat… |
| P10 / P11 | Octave down / up (P0: root) | Base octave − / + | Drum pitch −1 / +1 (P0: kick preset) |

Labels for the printed panel, chosen by hand: pads by scale degree on line 1 (`1 · root` … `7`), the drum on line 2. Degrees stay right in every scale and key; note names wouldn't (SW1 and P0 + P10/P11 move them).

Still leaking from outside the mode sections: the Recording section (a sub-mode of Seq, at the same heading level) fills Seq's P2 + S35.

### Later ideas

- The visualizer (`visualizer/`, Vite) talks to the hardware over MIDI telemetry and has a mock transport. A transport backed by the wasm build would let it run without hardware: the firmware's own page and the library playing the same build.
- Settings persistence through `localStorage` would make the browser build remember its sound between visits.

## Trust rule while builds live in forks

The library plays a build only from the firmware's own repository (raw files or its owner's Pages), pinned by sha256. Builds of the officials made in `jonwaterschoot/<official>` forks are not that. Either keep them local (localhost is allowed), or add an explicit, visible allowlist ("unofficial build") in `core.js`. Never relax the rule silently.
